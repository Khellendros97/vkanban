### Findings

#### Major

**M1 — 缺少 pi_exited_no_callback 兜底路径测试** (`src/worker.ts:67-71`)

当前测试覆盖了 `spawn_failed`（`tests/unit/worker.test.ts:59-69`、`tests/e2e/picrash.test.ts`）和正常写回（`tests/unit/worker.test.ts:37-57`），但缺少 pi **成功 spawn 后退出时未调用 `-s`/`--fail`** 的兜底测试。这是 worker 中最关键的容错路径，应在单元测试中覆盖。

影响：回归风险 — 若 future 修改破坏了 fallback 逻辑，不会被现有测试捕获。

建议修复：在 `tests/unit/worker.test.ts` 或 `tests/e2e/picrash.test.ts` 中新增一条测试：插入 pending 任务，使用一个 exit 0 但不写回的 fake pi，验证任务最终被标记为 `failed/pi_exited_no_callback`。

---

**M2 — daemon 缺少优雅退出信号处理** (`src/worker.ts:78-86`)

当前 `runDaemon` 的 `while(true)` 循环没有任何 `SIGINT`/`SIGTERM` 信号监听。当 Windows Service（`sc.exe stop`）或终端 `Ctrl+C` 终止 daemon 时，若正好处在 pi 执行期间，任务会**永远留在 `running` 状态**。`sc.exe stop` 最终会强制终止进程，不会有回调机会。

影响：Windows Service 场景下停止服务时，正在执行的任务变为僵尸状态（`running` 且无 worker 认领）。

建议修复（按优先级）：
1. **至少文档化**：在 README 中说明 daemon 被终止时当前任务将留在 `running` 状态，可用 `vkanban -t <id> --fail "daemon stopped"` 手动清理。
2. **建议实现**：监听 `SIGINT`/`SIGTERM`，在收到信号后不启动新任务，等待当前 pi 退出（或超时强制标记 failed），然后退出。

---

**M3 — `which()` 在 `splitCommand` 之前使用可能产生未定义行为** (`src/worker.ts:34-35`)

```ts
const rawPiCmd = Bun.env.VKANBAN_PI_CMD || "pi";
const piCmdParts = splitCommand(which(rawPiCmd) || rawPiCmd);
```

`which(rawPiCmd)` 按 PATH 搜索**整个字符串**。若 `VKANBAN_PI_CMD` 设为 `"bun run script.ts"`，`which()` 会尝试在 PATH 中查找名为 `"bun run script.ts"` 的文件（含空格），必然找不到，然后 fallback 到 `splitCommand(rawPiCmd)` 正确拆分。这个路径虽然功能上正确（fallback works），但逻辑意图混乱。

影响：代码可读性问题，无功能 bug。

建议修复：先 `splitCommand`，再对第一个 token 使用 `which()`：

```ts
const parts = splitCommand(rawPiCmd);
parts[0] = which(parts[0]) || parts[0];
const piCmdParts = parts;
```

---

#### Minor

**M4 — `splitCommand` 不处理带引号的参数** (`src/worker.ts:16-18`)

`raw.split(/\s+/).filter(Boolean)` 会把 `"C:\Program Files\bun\bun.exe" run script.ts` 拆成 `["\"C:\\Program", "Files\\bun\\bun.exe\"", "run", "script.ts"]`。使用 `splitCommand` 时若路径含空格，会错误拆分。

影响：仅影响 `VKANBAN_PI_CMD` 包含引号或含空格路径的场景。当前默认值 `"pi"` 不受影响。

建议修复：使用 `Bun.spawn` 的 `{ shell: true }` 选项（让 shell 解析引号），或实现简单的引号感知分割。

---

**M5 — `runDaemon` 在处理完任务后立即再次轮询，无冷却间隔** (`src/worker.ts:83-86`)

```ts
if (result.status === "idle") {
  await new Promise((resolve) => setTimeout(resolve, options.pollIntervalMs));
}
```

当 `status === "processed"` 时，daemon 不 sleep 直接进入下一轮。若任务处理极快（如 spawn 立即失败），会导致紧循环。设计 spec 未明确要求这个冷却，但这是常见最佳实践。

影响：CPU 占用略高（spawn 失败场景），非功能性问题。

建议修复：在 `processed` 后也加入一个极短的 sleep（如 `pollIntervalMs` 的下限，约 10ms），或统一在循环末尾 sleep。

---

**M6 — `casPendingToCancelled` 对不存在任务返回 `error_code: null`** (`src/tasks.ts:78-92`)

当 `taskId` 完全不存在时，返回 `{ changed: false, status: "unknown", error_code: null }`。`error_code: null` 与 `status: "unknown"` 语义上不一致（unknown 状态的任务不应有 null error_code）。但实际调用路径（`src/commands/cancel.ts`）会先做 `getTaskById` 检查，所以不可达。

影响：仅防御性代码路径，不可达，无实际 bug。

---

#### Nit

**N1 — daemon 命令 catch 块中使用了 `process.exit`** (`src/commands/daemon.ts:28-30`)

```ts
} catch (error) {
  console.error(JSON.stringify({ status: "error", message: String(error) }));
  process.exit(1);
}
```

项目中约定使用 `Bun.env`（而非 `process.env`），但 `process.exit` 是 Bun 中的标准退出方式，其他命令也在使用。风格一致，不合理议。

## Review-0004 (Post-merge fix)

**Issue:** `vkanban service start` failed with error 1053 — Windows Service requires SCM-aware binary. Our daemon is a console app, not a service binary.

**Root cause:** `sc.exe create` registers the binary with Windows SCM, which expects `StartServiceCtrlDispatcher` + status reporting within ~30s. `bun run daemon` is a plain console app and doesn't implement the SCM protocol.

**Fix:** Replaced `sc.exe`-based Windows Service approach with `schtasks.exe` (Windows Task Scheduler):
- `install`: `schtasks /create /tn vkanban-daemon /sc onstart /ru SYSTEM /rl HIGHEST`
- `uninstall`: `schtasks /delete /tn vkanban-daemon /f`
- `start`: `schtasks /run /tn vkanban-daemon`
- `stop`: `schtasks /end /tn vkanban-daemon`
- `status`: `schtasks /query /tn vkanban-daemon /fo LIST`

Task Scheduler runs daemon as SYSTEM on boot, outside user session — same isolation benefit, no SCM protocol required.

**Files changed:**
- `src/service.ts` — `buildServiceCommand` now builds `schtasks.exe` commands
- `src/commands/service.ts` — removed `--display-name` (not applicable), updated descriptions
- `tests/unit/service.test.ts` — updated to match schtasks argument format
- `README.md` — "Windows Service" → "Windows 自启（Task Scheduler）"

**Verification:** `bun test` → 64 pass / 0 fail
